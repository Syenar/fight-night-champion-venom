## Findings

1. **The earlier PE-loader and PPC32 conclusions are invalid for the effective guest-memory image.** The Xenia-shaped memory image must be imported at base `0x82000000` and interpreted using the loader-derived section map. PPC64 instructions are present: saved PPC64 disassembly at `0x82297D58` is `subfe`, and `0x8229B36C` is `ld`. The prior `PowerPC:BE:32:default` analysis did not provide trustworthy decoding/function evidence for these sites. Historical files remain preserved; their conclusions are not used to guide changes.

2. **The standard PPC64/32-address project is completed and saved.** `research/ghidra/FNC_TU2_PPC64_32addr_DecodeOnly_20261007` uses `PowerPC:BE:64:64-32addr`, the 12-section protection map, clipped out-of-image `.reloc`, and seeded XEX entrypoint `0x82297338`. Full analysis completed in about 339 seconds. The separate read-only critic verified the saved program's RX `.text`, RW/NX `.data`, inaccessible header gap, entrypoint, selected function ownership, and instruction bytes. This validates those sampled windows; it does not certify all discovered functions or complete decompiler output.

3. **The A2ALT experiment was not a saved full analysis.** The `PowerPC:BE:64:A2ALT-32addr` experiment ran with `-readOnly`; Ghidra discarded autoanalysis changes. Its targeted decode is a comparison only. Do not report it as a second completed analysis. The standard PPC64/32-address project remains the saved reference for this pass.

4. **Warnings still need range-aware triage.** The PPC64 full analysis emitted p-code warnings and embedded image-format analyzer errors. No evidence currently classifies every warning address as executable code versus embedded/data bytes. The selected PPC64 instruction windows were verified separately. Treat affected decompiler output as untrusted until each warning is tied to a mapped executable instruction and reproduced in an isolated decode.

5. **`0x82297D58` is a false lead for the current startup stall.** Saved Ghidra decodes `subfe r3,r10,r11`; the generated function `0x82297CA0` implements it inside block `0x82297D4C` and continues at `0x82297D5C`. The generated v2 registry does not expose it as an independent canonical function entry. The old `0x58470001` fallback trap belongs to a different runtime/build state. It does not establish a current decoder defect, and no alternate-entry hint is warranted from this evidence.

6. **The old `0x82C80030 -> 0x82EE2B1C` repetition is a separate historical symptom, and its source-level repair is not runtime-proven at that exact site.** The older `tu2-subfe` observations report repeated dispatch at `0x82EE2B1C`; that run did not record a runtime-host hash. Current `XenonSession::call` returns a handled recognized import to aligned guest LR using `FlowReason::Return`, which matches the old thunk's apparent control-flow problem. The 60-second current-host run did not reach that exact site. Preserve this uncertainty; it is no longer the immediate trace target because a later probe progressed to different startup activity.
7. **The first `0x58470004` trap at `0x82297B14` was a 4,096-instruction safety-budget stop in a real array scan, not an unsupported opcode.** The 16-instruction ring repeatedly captures `0x82297B0C..0x82297B30`: load the current word, compare to zero, increment `r31` by four, compare against the end pointer in `r30`, and loop while below the bound. In the 4,096-instruction run, `r31=0x82EF1D3C` and `r30=0x82EFED70`, leaving 13,325 four-byte entries. The same loop is present in generated `xenon_fn_82297A70_dispatch_v2` in `shard_010.cpp`. The earlier log's `cia=0x82297B14` was stale; the diagnostic fix now reports the actual next stop PC `0x82297B28` and word `0x3BFF0004`.
8. **The fallback branch-entry return boundary and trap-PC diagnostics are fixed and regression-tested, but that branch-boundary change did not itself resolve the game's array scan.** A dynamically decoded block entered as `Branch` must propagate a `blr` to its inherited LR as `FlowReason::Return`, rather than decoding the caller continuation as part of the block. A direct branch-entry return regression was added; the instruction-limit test now uses sequential NOPs and verifies stop PC, CIA/NIA, word, and ring trace. `xenon_dynamic_fallback_tests` and 960 semantic comparisons pass. The exact-TU2 probe still hit the 4,096 limit; only the probe-local higher ceiling passed that long scan.
9. **The 250,000-instruction exact-TU2 probe passed the scan and continued startup services, but did not demonstrate a booted game.** It used the same canonical effective image (`b771b41caef2483549bfbc7d726be3eb56943f99`) and generated module; `dynamicFallbackMaxInstructions=250000` was confined to its launch config. It recorded no fallback instruction-limit event and no guest trap, then continued through additional loader/kernel calls, including repeated `KeDelayExecutionThread` on guest thread 10. It remained running without a frame. A stop signal failed to end all guest execution within the five-second grace, after which the host was terminated and reported `Stopped: game did not exit cooperatively and was terminated`. This is progress evidence, not a pass; do not raise the default budget based on this probe.
10. **The worker-delay behavior and failed cooperative stop are the next unresolved runtime questions.** The probe log contains 9,684 `KeDelayExecutionThread` calls, 9,676 attributed to guest thread 10. Its interval pointer is `0x3FAC7AB0`, but the pointed-to 100-ns value was not logged. Thread 2 also returned `STATUS_TIMEOUT` (`0x102`) from `NtWaitForSingleObjectEx`. Call counts alone do not show whether thread 10 is doing a normal finite delay, a zero/expired yield, or a bad poll, and the trace does not identify which thread prevented shutdown. Capture the interval value and per-thread stop state before changing timing semantics.
11. **The canonical image and Xenia post-load dump remain distinct.** The pre-map effective image is 20,316,160 bytes, SHA-256 `EBDCBE683DB2F1C29AA43AC97E79492926C099B2EE253DB502CABCBEC133D52F`, and runtime SHA-1 `b771b41caef2483549bfbc7d726be3eb56943f99`. The older Xenia post-load capture differs in 5,700 bytes across 343 ranges. Different loader stages are plausible, but the byte differences have not been classified and must not be normalized away.
