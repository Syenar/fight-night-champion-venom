## Probe admission and lifecycle

Before launch, create a private `research/repair/<issue-id>/attempt-N/probe-manifest.json` with:

- Exact source/TU2/module/host/config hashes, renderer, headless mode, fallback limits and isolated save/output paths.
- Hypothesis, supporting evidence, discriminating expected observation, trace points/caps, maximum duration and stop/termination policy.
- Exact command, working directory, environment changes and regression scenario.

Run through a retained foreground/debugger session or a supervisor that waits for the actual child and persists exit evidence. Retain PID, start/end times, exit code, terminal/debugger output and final status. Do not detach through a short-lived shell and assume the child survived. Bound initialize/load/start as well as execution. On failed cooperative stop, preserve the snapshot and label watchdog/forced termination. Exit 0 alone is not clean shutdown. Restore diagnostic environment changes afterward.

After each run, classify the hypothesis SUPPORTED, DISPROVEN or INCONCLUSIVE separately from card status. Record progress to the predicted transition, fallback use, service failures, graphics evidence and shutdown. An absent capped trace cannot prove a call never occurred. Invalid measurement requires repaired measurement, not a semantic patch.

Do not repeat unchanged experiments. If the same outcome returns without new discriminating evidence, inspect the caller/service contract or repair instrumentation before another broad run. Three repair cycles require distinct evidence-backed changes; inventing patches to meet a count is forbidden. Exhausted hypotheses require primary-source research or a documented runtime/tool alternative with adapter validation, not reduced scope.
